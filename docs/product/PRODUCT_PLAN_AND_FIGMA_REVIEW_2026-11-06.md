## 1. 计划书真正提出了什么

标题：**《Will 项目计划书：面向大学生日常任务的 AI 工作台》**。目标是将分散通知、模糊意图或上传资料整理成**项目、任务、资料卡和日程**，核对后保存，并支持后续改期、提醒、进度跟进。重点场景：
- 课程论文 / 小组作业：需求与参考材料 → 计划卡 → 分步任务与时间安排 → 再次修改；
- 资料整理 / 报名申请等长周期事务：带来源的摘要与资料卡、流程模板、材料清单、节点提醒；
- 多人约时间：邀请填报、共同空闲、定档、变更与私密性；
- 通知转日程 / 抢约提醒为相邻场景。

产品组在第 3 节提出**八类工作入口**：日程、抢约、任务项目、资料、流程跟进、论文、多人协作、聊天。AI 对话与工作区双向关联；结果卡必须允许人核验与修改，失败/重试应保留进度。工作记忆保存个人偏好，业务数据记录任务及日程。

第 2 节用滴答清单、Notion、飞书做对照，重点主张用**同一个真实任务**比较操作成本。第 9 节建议邀请 **8–12 位目标学生**，观察**约两周**的使用，记录能否独立完成、需要帮助的次数、结果是否被采用、几天后是否回来。这里是**试用建议**，并非已发生的用户试验结果。

第 6–7 节整理了技术组提出的 C++ 服务端、SQLite 与缓存、模型工具调用和 TCP/TLS 长连接；同时承认产品组的响应式网页与服务端连接、流式传输、文件解析和协作仍需共同确定。它们是**方案与待对齐问题**，不是本仓库已实现的 API。

## 3. 与当前 React/Electron Windows 版本怎样对应

| 能力 | Windows 展示版（PR #3） | 产品组材料中的方向 |
|---|---|---|
| 项目 / 待办 / 日历 | 已有真实本地数据联动，完成/恢复、编辑和持久化 | 扩展为长期任务、论文、流程之间的统一工作区 |
| AI 输入及结果确认 | 本地规则模拟识别，结构化草案可编辑确认 | 结合当前工作区上下文、资料来源与多轮补问 |
| 首页 | 双栏卡片、近期与今日截止、项目及日历 | “今天”的重要事务、可用时间和当前项目更聚焦 |
| 资料库 / 论文 / 流程 / 协作 | 尚未作为完整功能交付 | 计划书和 14 页视觉稿中的候选扩展方向 |
| 提醒 | 当前仅保存提醒偏好 | 站内 + 浏览器通知、补发与状态显示 |
| 技术载体 | React + TypeScript + Vite + Electron 的 Windows 包；AI 与服务端尚未连接 | 产品组倾向响应式 Web；技术报告提出 C++ 服务端与 TCP/TLS |

**需要对齐的是产品路线和具体接口契约，而非简单选择把哪个 UI 截图替换到现有代码。** React UI 可继续支持 Web 和 Electron 两种载体，但还没有团队统一的发布决定。

## 4. 认可的设计判断

1. 核心价值更加清楚：从“创建一条日程”扩展为“同一任务的信息、行动与后续修改可以接续”。这有机会回应原先学生信息散落、遗漏和反复查找的问题。
2. 结果卡、**先核对再保存**、来源可回查、缺失时补问、失败继续，是相互支持的设计。我们的 P0/P1 交互已经提供了部分基础。
3. 同任务对照与两周使用回访具有检验价值，尤其关注“过几天能否继续用”，比只看初次演示更接近实际产品价值。
4. 协作部分提出的“仅共享忙闲、不泄露日程标题、可撤销授权”有清晰的隐私边界意识。
5. 视觉稿页面间的主导航、卡片、字体和状态样式较一致，已能作为讨论信息架构与典型场景的素材。

## 5. 优先讨论的问题

### A. 八类工作入口的优先级仍不明确（最重要）

计划书描述了大量功能与未来价值，但缺少能驱动开发的**第一阶段/第二阶段范围、负责人、完成条件、依赖关系**。对经验有限的学生团队，同时实现文件解析、论文工作台、协作权限、通知和真实 AI 的负担很高。

建议用一条纵向场景作为下一阶段验证重点：**粘贴一条真实校园通知 → 识别具体任务、时间与来源 → 用户校对 → 保存为日程/待办 → 数天后重新打开并修改**。与现有 Windows 功能的距离较短，也可与人工整理/现有日历做比较；若团队认为论文任务更重要，应使用同样的方法先选**一个**具体论文案例，不并行开发八入口。

### B. 两份资料中视觉基准尚需确认

计划书第 5 节嵌入了 **深色**的 Figma“对话工作台”和“日程页面”（节点 `2:60`、`2:61`），而这次上传的 14 页 PDF 是**浅色**并采用不同的信息编排。当前已验收的 React/Electron 版又是另一套已运行实现，且支持深浅主题。

目前不能从材料判断哪一套视觉已获组内最终批准。建议产品组先说明：是同一设计的不同方案、深浅主题稿，还是阶段性草稿；明确哪些属于**必要的交互规则**、哪些只是**视觉参考**。不宜直接重做客户端。

### C. 信息架构与上下文归属

14 页视觉稿左侧菜单非常丰富（项目与待办、流程跟进、资料库、论文工作台、协作空间、AI 等）。对新用户的导航负担可能偏大。产品组需要明确：
- 一个论文项目里的任务、文件、日程，究竟是一处编辑、多视图查看，还是各入口保存不同记录？
- 从论文工作台切换到 AI 助手时，当前项目/文件如何保留和展示？用户如何知道 AI 正在处理哪个项目？
- “提醒”“流程节点”“待办截止”之间是否共用业务对象？避免三处各改一次。

建议优先建立对象与关联关系的统一说明，再决定是否让八类工作入口都常驻侧栏。

### D. 视觉稿还缺少部分关键交互状态

十四页的静态画面可以说明页面构成，但无法证明输入、文件解析、取消、重试、授权、空数据、多人改期、冲突解决等流程已经闭合。现有截图已有登录错误、文件状态和待确认卡等局部示意，应继续补齐核心场景的**操作步骤和失败分支**。还需审查：
- 桌面内容在常用尺寸下是否过度集中于上半部，空白虽美观但信息密度/滚动结构是否合理；
- 文案、次要说明与低饱和文本在日间主题和不同缩放下是否足够清晰；
- 移动端是否真的需要 12 个导航入口，还是应按核心任务重排。

### E. 前后端协议边界需要落地

计划书同时引用 C++ 自定义 TCP/TLS、响应式 Web 与流式 UI。**浏览器页面不能像普通 TCP 客户端一样直接建立任意 TCP 套接字**。如果将来支持 Web + Electron，应先约定可用的浏览器侧 HTTPS / WebSocket / SSE 方案、认证、草案确认后写入的业务结果、错误与断线恢复，并以一条实际请求为验收。不要让 UI 直接依赖尚未明确的专用二进制传输格式。

## 6. 建议下一次产品/技术联合评审只作三个决定

1. **场景优先级**：下一个可用版本只验证什么真实校园场景，如何衡量“比现在更省力、愿意回来继续用”。
2. **信息模型与上下文**：项目、任务、日程、文件、AI 草案和来源之间的最小字段与关联；当前 UI 哪些已具备，哪些要扩展。
3. **设计与接口基准**：先认定当前演示版、深色 Figma、14 页浅色设计各自角色；后端给出一条端到端正式接口实例及浏览器可用的传输方案。

这些决定形成共识后，再确定具体开发 Issue，不建议在 11 月 7 日展示前临时新增全套资料、论文与协作功能。
