# Will 下一版 PC 前端：信息架构与交互构想（团队讨论稿 V0）

> 记录日期：2026-11-06  
> 状态：个人方案与讨论材料。提出者认可方案 A 的总体方向，尚未取得产品组 / 技术组正式共同确认。  
> 用途：帮助成员交流“为什么这样组织功能”，保留取舍依据；不直接充当开发需求、交付承诺或正式 UI 规范。  
> 技术边界：本轮仅讨论前端；保留现有已验收 Windows 展示版本，不改代码、不覆盖发布、不合并 Draft PR。

## 一、想解决什么问题

产品组《Will 项目计划书》的定位是“面向大学生日常任务的 AI 工作台”。其设想覆盖日程、抢约、任务项目、资料、流程、论文、多人协作与聊天。现有 React / Electron 客户端已经有日程、待办、项目、AI 本地模拟草案的完整基本操作，但首页与页面结构较偏向日历管理。

下一版的设计目标是：用户围绕一件具体的事情，能够收集信息、拆成行动、安排时间、保存资料、查看进展，并在数天后回来继续。AI 贯穿其中，生成内容要允许人工核对，最终结果必须能在相应工作区找回。

本轮关注 **功能区域、信息架构、布局与真实连贯的前端交互**。已有 React 日间主题与产品组 14 页浅色视觉稿较接近，优先复用现有设计体系，不因视觉稿页数而增加同等数量的一级导航。

## 二、当前倾向：方案 A——以工作对象组织

建议的一级工作入口：

| 入口 | 用户到这里做什么 | 主要内容 |
| --- | --- | --- |
| 今天 / 首页 | 看清当前重点、继续未完成的工作 | 重要任务、临近截止、日程、进行中项目、AI 待确认、最近资料 |
| 项目 | 推进课程作业、论文、申请等长期事务 | 项目概览、任务看板、资料、按需启用的流程 / 论文 / 协作视图 |
| 资料库 | 收集、查找与追溯信息 | 文件与资料卡、来源、标签、解析状态、项目关联 |
| 日历 | 查看与调整时间安排 | 月 / 周视图、事件、截止、必要的时间冲突与约时间入口 |
| AI 工作区 | 整理输入、处理草案、围绕当前工作提问 | 对话 / 输入、结构化结果、历史与待确认草案、上下文 |

全局工具：**搜索、提醒 / 通知、快速添加、设置**。AI 另有随手呼出的辅助面板，用来在当前项目或资料页面中执行轻量操作；复杂任务与历史会话留在独立工作区。

论文写作、流程跟进与多人协作目前建议优先作为 **项目内的专门工作视图**；协作约时间可与日历联动。“抢约”不急于独立占用一个主导航。独立资料库继续存在，方便跨项目检索。个人杂项可归入“个人事务”等默认项目。

上述入口是设计建议，正式命名、具体数量与项目内视图范围仍需讨论。

## 三、功能之间应怎样关联

建议先明确共用对象，再决定各页面显示哪些视图：

- **项目**：工作的组织单位，持有 ID、名称和生命周期；同一项目下可关联任务、日程、资料、流程、成员和 AI 记录。
- **任务 / 日程**：统一的数据对象。可以出现在首页、项目和日历；在一处修改后，其他页面即时更新。
- **资料与来源**：资料有自己的身份与来源记录，可关联一个或多个项目；AI 摘要与操作建议能回查原始信息。
- **流程 / 论文**：可理解为项目模板及专用视图，流程步骤或论文大纲另有自己的内容；其中实际待办继续复用统一任务。
- **AI 输入与草案**：保留输入内容、关联上下文和状态；用户确认后才生成正式任务 / 日程 / 其他结果。未确认内容应可暂存、继续编辑或放弃。
- **提醒、协作**：跨页面能力。提醒应指向相关任务 / 日程 / 流程节点；多人忙闲、邀请与权限的真正执行留待后端。

例如：“提交论文初稿”在论文项目中是同一项任务，首页可提示它即将截止，日历按截止日期展示它，AI 对话可以基于它提出调整建议。不能形成三份需要分别修改的记录。

## 四、推荐的桌面页面组织

- **左侧导航**：常态可用约 180–210px 的可折叠侧栏，紧凑状态沿用现有约 88px 导航思路；常用窄窗口优先自动采用紧凑布局。具体尺寸以真实 Windows 窗口测试再定。
- **顶栏**：提供全局搜索、快速添加 / 收集、提醒与账户入口；不要求用户返回首页才能新增内容。
- **首页**：最重要的是“今天关注什么、从哪里继续”，日历只承担一个时间概览区块。保留现有临近截止、任务完成进度及项目概览的成熟逻辑。
- **项目详情**：根据项目类型显示概览、任务、资料、论文大纲、流程、协作等标签或子视图。任务看板需要能拖动或通过菜单改变状态，任何变化实时反映到相关列表。
- **AI**：保留现有可用的右侧抽屉；另设完整工作区处理长对话、多个结果、草案与历史。进入 AI 时清楚显示当前关联项目 / 资料，可主动切换上下文。
- **视觉**：参考产品组的留白、蓝色主操作、细边框卡片和清楚的状态色，保留现有日夜主题；14 张 Figma 作为设计素材和页面结构参考，不要求逐张复刻。

## 五、用三条连续操作验证设计

1. **校园通知 → AI 草案 → 人工确认 → 保存**：用户粘贴通知，Mock AI 给出可编辑的任务 / 日程，缺字段必须补全；确认后项目、首页、日历同步更新，来源可回查。取消、失败和重试均保留适当状态。
2. **课程论文 → 项目工作台 → 资料 / AI**：用户创建论文项目，看到任务、参考资料和大纲；从项目呼出 AI 获取建议，确认后的行动回到该项目，离开页面后能继续编辑。
3. **小组作业 → 约时间 → 日历**：项目成员的模拟忙闲供用户选择，确认会议时段后进入统一日历；界面应明确为模拟，不冒称已经发送邀请或同步到真实成员。

关键验收问题：从任何入口创建的对象，在对应工作区能否找回？改期、完成、归档和 AI 确认后，各处展示是否一致？返回应用后能否继续上次的工作？

## 六、为什么倾向 A；保留哪些不同意见

| 比较角度 | A：围绕工作对象 | B：围绕专业功能 |
| --- | --- | --- |
| 用户思路 | 先找到“课程论文 / 小组作业”，再使用任务、资料、AI | 先选择“论文 / 流程 / 协作”等工具 |
| 主导航 | 数量较少，项目上下文连续 | 各种功能更显眼，新用户容易直接发现 |
| 功能关联 | 同一项目的内容集中管理 | 跨工具找回同一项目内容的路径较长 |
| 主要代价 | 项目详情可能变复杂；必须做好标签、模板、搜索和快捷入口 | 导航更多，也更容易让用户把同一事务分散在多个模块 |

当前个人倾向 **方案 A**，认可产品组专业功能的价值，建议通过项目模板和专用视图保留它们的完整体验。此选择目前是讨论倾向，**不代表产品组已同意撤掉论文、流程或协作等独立入口**。

## 七、现有实现能复用什么

以 Windows 展示基线 PR #3 为准：

- 可重点复用 React / TypeScript / Vite、Ant Design、深浅主题、Electron 包装与构建、日历和任务领域逻辑、项目增删改归档、AI 草案编辑 / 校验 / 确认、空态与持久化规则。
- 需要扩展：目前的四页面状态导航、结构简单的 Project 类型、项目详情 / 看板、资料与来源模型、持久化草案箱、AI 上下文和多类型结果卡。
- 纯前端可先用 Mock 数据及可替换接口实现操作、状态流和跨页面联动；复杂解析、真实模型、登录、多端同步、协作权限和系统级提醒由后续后端 / 桌面能力接入。
- 前端仍应负责校验、错误 / 加载 / 空态、确认及重试。不要把“上传文件名”当作已经保存了文件，也不要将本地模拟的协作或提醒说成真实服务。
- 不破坏现有版本 2 日程数据、历史本地数据兼容和已验收的 Electron 运行路径。必要时将新模型放入独立、可迁移的数据存储。

## 八、建议的推进顺序（供讨论，尚未成为 Codex 工单）

**第一批：** 新导航、新首页、项目详情、任务看板、上下文切换，让“项目中心”先真正可用。  
**第二批：** AI 完整工作区与草案箱、资料库、来源关联和全局搜索，验证“信息到行动”的闭环。  
**第三批：** 论文 / 流程专用视图、协作与约时间 Mock，覆盖产品组设想的更多典型校园任务。

开发时可复用组件与 Mock 接口，分批验收。工作量应区分界面调整、前端模拟交互、真实后端接入三个类别；以上顺序不是时间或交付承诺。

## 九、后续与团队需要共同决定

1. 方案 A 的一级导航及项目内的论文 / 流程 / 协作视图，是否符合产品组的定位？哪些能力确实值得一级直达？
2. 第一条需要完整演示的真实校园场景，是通知整理、课程论文，还是小组协作？选择依据是什么？
3. AI 输入、草案、资料来源和项目的关联应保留哪些字段？草案应保存多久？
4. 正式资料文件持久化、AI 协议、提醒和多人权限由哪些服务提供？Mock 阶段如何准确标记？
5. 产品组浅色 14 页视觉稿与计划书中的深色画面，各自用于什么，哪些交互已经达成团队共识？

## 十、对外说明的简短说法

> 我倾向把 Will 做成围绕具体学习和校园事务运行的 AI 工作台。进入一个课程论文或小组作业项目后，任务、资料、日程、AI 和后续协作能够持续衔接。主导航先按“今天、项目、资料库、日历、AI”组织；论文、流程、协作保留为项目内的专业视图。这样既保留产品组设想的丰富能力，也有利于复用目前已经完成的 Windows 前端。现阶段先用 Mock 打通真实操作与数据联动，后续再按约定接入服务端。这是供产品组和技术组讨论的方案，具体布局和开发顺序仍需要一起定。
