## 1. 产品目标与一条原则

Will 从当前偏重日历的个人安排助手，扩展为围绕校园真实事务运行的 AI 工作台：用户可以**收集信息 → 理解与核对 → 组织项目 / 任务 / 资料 → 安排时间 → 跟踪进度 → 隔天继续**。

核心原则：**同一个对象只有一处真实记录，允许多个工作视图。** 例如一个论文任务在项目看板、首页和日历中都能出现，修改截止时间后同步更新；一份通知可作为来源被任务、资料和 AI 草案共同引用。

产品计划书的八种工作能力是规划素材，不直接等于八个顶层菜单；产品组 14 页浅色 Figma 是布局与视觉参考，现有 React 白天主题已有相近基础，保留夜间主题。

## 2. 推荐信息架构

建议主工作入口：

1. **今天**：重要待办、近期截止、继续工作、正在推进的项目、等待确认草案、少量今日时间安排。减少“月历与统计占据首页”的权重。
2. **项目**：项目列表 → 项目详情。详情内建议有“概览 / 任务 / 资料”，根据项目模板启用“论文 / 流程 / 协作”等专用视图。初期不把每个专业能力都做一级导航。
3. **资料库**：跨项目查看通知、文字资料、链接和文档卡片；有来源、内容 / 摘要、关联项目与使用记录。项目内资料是这个库的过滤 / 关联视图。
4. **日历**：复用现有月历及日期安排；显示有时间的事件、具有截止日期的任务和提醒标识。可逐步增加周视图、倒计时、时间冲突处理。
5. **AI 工作区**：完整输入 / 对话、上下文、生成中的状态、不同类型的结果卡、草案箱、历史；现有右侧 AI Drawer 保留为全局轻量入口，复杂操作进入独立页面。

全局操作：**搜索、快速添加 / 粘贴信息、提醒 / 通知、设置**。全局按钮应有可操作的真实行为；尚未开发的能力不得摆成假装可用的按钮。

导航方案 B（论文、流程、协作等独立一级入口）仍作为备选，优点是专业模块显眼。方案 A 的代价是项目详情可能变复杂，应通过项目模板、标签分组、快捷跳转和搜索弥补。产品组未正式确认之前，不据此删除其专业能力诉求。

## 3. PC 主窗口与页面交互

### 3.1 框架
- 保留现有 React、Ant Design、CSS 变量和 Electron 外壳。侧栏建议从现有 88px 窄图标栏扩展为**可折叠侧栏**，桌面展开宽度约 180–210px；窄窗口保留紧凑栏。数值是讨论值，需用实际窗口测试决定。
- 顶栏放搜索、快速添加 / 收集、提醒、账户 / 设置；“AI 助手”可在各工作区呼出，显示当前项目或资料上下文。
- 主区按功能采用不同版式：首页卡片、项目看板 / 列表、资料列表 + 预览、论文大纲编辑、日历视图。避免每页都复制同一种双栏卡片。
- 页面导航应保留项目 ID、选中资料和当前视图，以支持跳转、返回、重启后找回工作。当前 App.tsx 的 `PageKey` / `ShellPages` 只适合四页，需逐步引入有路径和参数的导航。建议 Codex评估 hash 路由是否最符合 `will://app/` 离线桌面协议，禁止直接假定 BrowserRouter 深链接可用。

### 3.2 页面具体要求

**今天**：
- 重要事项：未完成且逾期 / 即将到期优先；不要仅凭“今天截止”代替今日需要处理的任务。
- 继续工作：可点击具体项目或最近访问的工作内容，打开相应详情与标签页。
- AI 待确认：显示未确认的草案批次，点击回到编辑确认界面。
- 时间预览：今日事件或紧凑日历。现有进度、近期截止、筛选与搜索逻辑可以复用，但首页首屏要把“做什么、继续哪里”放在首位。
- 空态：无项目、无任务、仅有事件、所有任务已完成等情况有正确导向。

**项目列表 / 详情**：
- 列表支持新建、查看、改名、归档 / 恢复；项目卡显示进度、临近任务、最近活动。
- 项目详情上方固定项目名称、状态、快速添加和 AI 上下文提示；标签“概览 / 任务 / 资料”，专门视图按模板显示。
- **已获用户确认的项目详情结构（2026-11-06）**：所有项目默认拥有 **概览 / 任务 / 资料** 三个基础视图。按项目类型或用户需要，额外启用 **论文 / 流程 / 协作** 等专用视图。此为前端方案中已认可的产品原则；具体标签数量、视图启用 / 隐藏方式和团队级最终决定仍待讨论。
- **概览**：项目目标、重要任务与近期截止、进度、最近资料和继续操作入口；不要重复整页任务看板。
- **任务**：同一套项目任务数据的看板 / 列表展示，允许无截止任务，状态变更在首页与日历等视图同步。
- **资料**：按当前项目过滤同一个资料库中的资源，支持新建关联、查看来源与解除关联，避免形成项目内独立副本。
- **专用视图**：论文承载大纲与写作进度；流程承载阶段与材料清单；协作承载成员与约时间。它们可引用公共任务、日程和资料对象，不重复维护。

#### 项目创建与模板：已认可“预设模板 + 自由调整”（2026-11-06）

- **创建流程**：用户填写项目名称，可选择“普通项目、课程论文、流程申请、小组协作”等少量模板；模板仅用于提供初始视图组合和必要的结构提示，不应在创建时强迫用户填写大量字段。
- **基础视图固定可用**：所有项目都可使用“概览 / 任务 / 资料”。模板按需初始启用论文、流程、协作等专用视图；一个项目可同时启用多个专用视图。
- **允许随时调整**：项目建立后，用户可以添加、隐藏或重新启用专用视图，无需重建项目，也无需被初次选择的模板永久限制。模板选择不是排他且不可变的项目类型。
- **数据保护**：隐藏某个视图只改变显示配置，**不删除**其中已有论文大纲、流程步骤、协作记录或共用任务 / 资料；重新启用时可以继续此前内容。确需删除数据时应有单独、明确的删除操作与确认。
- **最小数据建议**：在项目对象之外或其兼容扩展中保存 `templateId`（初次创建使用的预设）与 `enabledViews`（当前启用视图），二者不互相覆盖；不得为了模板复制任务、日程和资料。
- **Mock 边界**：专用视图暂未实现完整内容时，可显示清楚标注的演示内容或空态，不假装已完成 AI 解析或真实协作。W1 优先实现模板选择、视图启用 / 隐藏的状态管理及持久化；具体专业编辑功能留在 W4。
- **交互验收**：选课程论文模板创建项目 → 有三种基础视图及论文视图 → 再启用流程视图 → 隐藏论文视图 → 退出并重启 → 视图配置仍在 → 重新启用论文视图，先前内容不丢失。

以上是用户同意的**设计方向**；模板正式名称、默认组合、是否允许调整标签顺序和项目级别权限仍待团队讨论。整体 V0.2 依然不是授权开发的正式需求。

- 任务提供列表与看板两种组织方式：**待处理 / 进行中 / 已完成**；第一批用菜单或按钮改变状态，拖拽可后加。
- **已确认的产品决定（用户，2026-11-06）**：普通任务可以完全没有截止日期；有截止日期的任务可以只填写日期、不填具体时刻；日历事件必须有明确开始日期和时间。三者分别按任务和事件规则展示。
- 点击任务可编辑标题、说明、所属项目、状态、可选截止日期；跨页立即可见。归档项目不丢任务历史。

**资料库 / 资料详情**：
- 可以增加粘贴文本、链接、演示资料卡；输入标题、来源及项目关联；可以改名、检索、移动或解除关联。
- 详情显示原始内容 / 来源、摘要、关联项目、所生成任务；支持从来源跳到任务，从任务跳回来源。
- 第一版不要假称已保存上传文件内容：若仅 Mock 文件卡，必须标注演示；要支持真正本地文件保存则需独立设计 Electron 安全的文件存储和权限方案。

**日历**：
- 继续复用现有月历、日期详情、任务完成 / 编辑、项目关联和状态颜色；视图中不展示没有截止日期的任务为假时间事件。
- 新项目工作区修改任务时间后，日历无刷新联动。若时间不合法或冲突，给出可理解的提示。

**AI 工作区 / 全局 AI Drawer**：
- 右侧 Drawer 做短文本整理、即时草案查看和跳转；完整页面用于长输入、历史、多个待确认结果、资料上下文。
- 一条完整状态流程：输入 → 模拟处理中（可取消）→ 生成建议 → 校验 / 编辑 / 移除 → 暂存或确认 → 写入共享数据 → 从项目 / 日历找回。
- 草案类型可扩展为任务、日程、资料卡、计划步骤；不同类型各自校验和目标保存规则。确认写入的批次要避免重复创建。
- 清楚标出当前上下文（当前项目 / 资料），允许用户主动切换；不能把全局 AI 对话隐含地绑定到错误的项目。
- 结果来源必须可回查。加载失败后输入和已编辑草案不应无故丢失。

**全局搜索 / 提醒 / 设置**：
- 搜索先扩展现有标题搜索至项目、任务、资料，结果按类型分组，点击跳到目标；后续再考虑全文检索。
- 提醒中心可先从现有截止数据推导“即将到期、已逾期”，提供前往事项、标记已读等本地操作；真正操作系统提醒仍未实现。
- 保留主题、名称、近期范围、示例与清空设置；扩展存储管理时避免意外擦除现有安排。

## 4. 数据关系与前端接口：Codex 必须先想清楚

建议的业务对象（字段示意，不是 Frank 已确认的服务端契约）：

- `Project`：`id,name,archived`，扩展描述、模板类型、展示排序等。
- `Task`：建议 `id,projectId,title,status,description?,dueDate?,dueTime?,sourceId?`；状态取待处理 / 进行中 / 已完成。**截止日期可空；仅在有截止日期时才可填写截止时刻，具体类型待技术设计定稿。**
- `CalendarEvent`：有确定时间的事件；保持与当前 `event` 领域规则兼容。
- `SourceRecord / DocumentRecord`：`id,type,title,sourceText?,sourceUrl?,projectIds[],createdAt` 与可追踪的来源状态。
- `DraftBatch`：`id,sourceId?,contextProjectId?,status,proposals[],createdAt`，包含可恢复的用户编辑结果。
- `Conversation`：`id,contextProjectId?,messages[]`（后续页面需要时引入）。
- `WorkflowStep / OutlineSection / CollaborationSession`：专业场景后续引入，勿先创建无用的复杂模型。

### 与已有本地数据的兼容

当前 `will-app/src/domain/schedule.ts` 使用版本 2 的 `ScheduleData`：`projects`、`tasks`、`events`；旧任务强制具备日期和时间，项目仅有 ID / 名称 / 归档状态。

**推荐方案**：Codex 首先提出并测试一个**统一数据权威来源**的升级路径（例如新的工作台版本化数据 key + v2 解码迁移），保留旧数据原值、旧 ID 与已验收的操作语义；不能让两个平行的“任务列表”各自成为真相来源。迁移应先在内存完成，用户明确变更时写入新版本，且有备份 / 回退办法。不要自动清空原键或覆盖展示版数据。

**已确认显示规则**：没有截止日期的任务保留在项目看板、任务列表和按需展示的首页任务区，不进入日历日期格与截止倒计时；只有截止日期、没有具体时刻的任务在该日期显示为「全天截止 / 日期截止」，不虚构 00:00 或 23:59 的精确时刻；有明确时间的任务按实际时间显示。日后设置或清除截止日期时各视图自动同步。

建议前端统一通过可替换的服务 / repository 读取与更新数据，Mock 负责本地保存、延迟 / 错误模拟、固定演示数据。独立的数据类型、适配和必要的错误状态要有，但不要为演示版搭建庞大后端仿真系统。未来 Frank 的真实接口需另行对齐认证、数据同步、解析、确认和错误契约。

## 5. 三条必须完整走通的场景

1. **校园通知 → AI → 项目 / 日历**：粘贴通知，生成任务与日程建议，显示原文，编辑含不确定字段，确认后跨页同步，重启可找回；暂存草案与取消也真实有效。
2. **课程论文 → 项目 → 资料 → AI**：新建论文类项目，查看任务看板与资料，关联原始资料，AI 给出建议并确认成任务；从资料能跳到任务、从任务能回到来源。
3. **小组项目 → 约时间 → 日历**（后期 Mock）：模拟成员忙闲、调整候选时间、明确人工定档，再写入日历；不会假装真实邀请已发送。

三条场景都有空态、加载、错误、取消、再次编辑、刷新和退出重进时的预期结果。

## 7. 建议的工作量量级（仅前端）

- W0：约 1–3 人日的调查 / 小规模验证。
- W1：约 4–8 人日；任务模型迁移难度会影响实际时间。
- W2：约 4–7 人日。
- W3：约 3–6 人日。
- W4：约 5–10 人日，按论文 / 流程 / 协作取舍波动很大。

数字是单开发者使用现有组件、Mock 和 AI 编码辅助的讨论级粗估，不是开发承诺，也不包含真实 AI 服务、服务器、文件解析、账号与真实协作。多个工作包复用基础时不能简单把极值相加当做工期。

## 8. Codex 工作方式与验收边界

- **开始条件**：本方案经用户讨论确认后，才授权实现。先从已验收的 `codex/windows-demo-2026-11-07` 源码基线另开实现分支 / worktree；参考 PR #4 文档，不将文档 PR 混同代码基线。
- **保持完整**：原 Windows 免安装 ZIP、PR #3、现有展示脚本和旧数据不可被新代码覆盖；不触碰 GitHub Pages 的 `main` 发布。
- **逐包提交 Draft PR**：每包尽量范围集中；跨包依赖写清楚，未被审阅的阶段不抢先实施后续功能。
- **验证优先**：已有 57 项 Node 测试及 PR #3 的桌面 / 网页回归基线不能无故消失；新场景补充领域、持久化、跨页面和浏览器验证。重点看 1440×900、1366×768、1280×720、1024×768；800×600 至少保证内容可访问，不能无提示溢出。
- **交互检查**：新增 / 编辑 / 删除 / 取消 / 确认 / 完成 / 恢复、搜索与跳转、无日期任务、坏数据兼容、重启持久化、Mock 错误 / 重试 / 取消以及深浅主题；按钮不得只有动画而不改状态。
- **明确事实**：任何 “AI 已识别、文件已上传、提醒已发出、团队已同步” 都必须对应真实能力，否则用可见标签说明 Mock / 演示。
- **报告方式**：给出可复现的场景、截图与测试结果，说明实现范围、未完成和设计取舍；避免过多与产品判断无关的工程日志。

## 9. 已确认原则与仍需讨论的设计问题

1. **已确认**：普通任务的截止日期、时间均可不填；仅有截止日期也合法；日历事件应有明确开始日期与时间。后续 Codex 须做数据兼容设计，但此决定并不等于已获编码授权。
2. **项目专用视图**：论文 / 流程 / 协作优先附着于项目详情，但是否允许常用功能同时有全局快捷入口？建议可以，避免项目页过深。
3. **第一轮产品验收重点**：W1 的项目看板与首页先独立验收，还是等 W2 AI 草案箱一起作为下一次团队演示？技术上建议分两批审阅，产品展示可合在一起。

## 10. 团队交流时可直接使用的一段话

> 下一版 Will 我想先从“日历助手”推进到“围绕任务和项目的 AI 工作台”。同一个课程论文项目里，任务、资料、日程、AI 结果能够互相跳转，用户过几天回来还能继续。主导航暂建议“今天、项目、资料库、日历、AI”，论文、流程和协作在项目中提供专门视图。我们会保留已做好的 React/Electron Windows 演示版，先用 Mock 做出完整、真实的前端操作，再逐步与后端接口对齐。这个方向是讨论提案，欢迎产品组对入口、界面和优先级提出不同方案。
